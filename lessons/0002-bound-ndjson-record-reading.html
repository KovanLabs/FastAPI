Read one NDJSON record safely

Today’s parser reads a bounded amount, classifies each line, and can continue after a bad record. This lesson explains what the code does, why its steps are ordered this way, and what remains unfinished.

What one outcome represents

ParseOutcome is a small envelope for the result of one input line. It prevents an ordinary bad record from aborting the whole file.

@dataclass(frozen=True)
class ParseOutcome:
    line_number: int
    record: dict[str, object] | None = None
    error_code: str | None = None
    skipped_blank: bool = False
  • line_number identifies where the outcome came from.
  • record contains the parsed object on success; otherwise it is None.
  • error_code names a failure such as invalid_utf8, invalid_json, not_object, or record_too_large.
  • skipped_blank distinguishes an intentionally skipped blank from a failure.

The implementation is in app/core/parsers.py.

The bounded-read sequence

binary stream → readline(maximum_record_bytes + 2) → remove LF / optional CR → enforce the raw-byte limit → strict UTF-8 decode → json.loads(text) → require a dict → yield one ParseOutcome
  1. Read at most a requested size. readline(size) returns no more than size bytes. The parser asks for the configured maximum plus two bytes so a maximum-sized record followed by CRLF can be recognized. See Python IO’s IOBase.readline(size) and Binary I/O topics.
  2. Measure the record, not its line ending. LF and an optional preceding CR are removed before counting. Other spaces remain part of the record size.
  3. Drain an oversized line. If it exceeds the cap, the parser discards the rest in bounded chunks through the next newline. That prevents the tail of one bad record from being mistaken for a new record. FastAPI’s “JSON Lines” topic describes the newline-separated record format.
  4. Decode strictly. The raw bytes are decoded as UTF-8 only after passing the byte cap. A UnicodeDecodeError becomes invalid_utf8. Binary streams do not decode bytes automatically; see Python IO’s Binary I/O and Text I/O topics.
  5. Parse JSON and check its shape. json.loads(text) can return different Python types, so valid JSON like [] is classified as not_object. Malformed JSON is classified separately as invalid_json. See Python JSON’s Basic Usage and Exceptions.
  6. Yield instead of accumulating. Each outcome is produced as the iterator advances. The parser does not build a list containing the whole dataset; callers could still use list(...) and retain everything, so production consumers must iterate or use bounded batches.

The mixed fixture and what it proves

The focused parser tests include a short valid–invalid–valid sequence and a mixed case with blank lines, CRLF at the exact size limit, invalid UTF-8, malformed JSON, a non-object JSON value, an oversized line, and a final valid line without a newline.

A tracking BytesIO records every requested readline(size) and asserts that none is unbounded. The tests pass with pytest -q tests/test_parsers.py.

Policy chosen for today: the size cap takes precedence over blank-line skipping. A whitespace-only line within the cap is skipped; a whitespace-only line larger than the cap is reported as record_too_large. This keeps the memory bound predictable.

The 1 MiB limit is a cap on raw record bytes, not a promise that the process uses only 1 MiB. UTF-8 text and the parsed Python dictionary need memory too; a batch can add more. Avoid converting the full iterator to a list when processing large files.

How chunks work for a JSON array

NDJSON can use newline as its record boundary. A JSON array cannot: a read may stop in the middle of a property name, string, number, or nested object. iter_json_array(chunks) receives byte chunks from its caller; it does not decide their size. For a file, the caller could repeatedly call read(64 * 1024), as described by Python IO’s IOBase.read(size).

file.read(64 KiB) → chunk 1 → chunk 2 → chunk 3 → … ↓ parser carries partial JSON state
chunks = [
    b'[{"id":',
    b'1},',
    b'{"id":2}]',
]

Those three pieces are deliberately split in the middle of the first object. A correct parser keeps enough unfinished bytes and state after chunk 1, completes {"id": 1} after chunk 2, then completes {"id": 2} after chunk 3.

The current implementation tracks nesting depth ({} and []), whether it is inside a quoted string, and whether the previous character was an escape. That matters because a brace inside a string—such as "note": "use } here"—must not close an object. Its current buffer/state handling has a known chunk-boundary bug: with the example above it returns only the first object. We confirmed this with the actual iterator, so the expected two-object result is a regression test, not current behavior yet.

Two memory details to fix: the current scanner checks an element’s size only after the element is complete, so an unfinished oversized element can grow the buffer too far. Also, feed() builds a list of all objects completed in one chunk before the outer iterator yields them. The eventual implementation must enforce the byte cap while reading and avoid unnecessary per-chunk accumulation.

ijson’s “High-level interfaces” also reads from a file-like stream and iterates matching objects; it is a useful reference design for incremental parsing.

Try the parser from Swagger UI

POST /imports/ndjson/validate is a separate incoming-upload endpoint. It stores the upload, reads the stored file in a worker thread, and consumes iter_ndjson one outcome at a time. The response includes valid and blank counts, counts by error code, and at most 20 failure samples; it never returns all parsed records. The existing POST /imports remains storage-only and keeps its queued response.

  1. Start the app with uvicorn app.main:app --reload.
  2. Open http://127.0.0.1:8000/docs and expand POST /imports/ndjson/validate.
  3. Click Try it out, choose a .ndjson file, then click Execute.
  4. Check valid_records, skipped_blank, failures_by_code, and the capped failure_samples. A malformed line should not prevent later valid lines from being counted.

The endpoint accepts application/x-ndjson and the generic application/octet-stream some browsers assign to unknown file extensions. It rejects an explicitly JSON-typed upload because JSON arrays need a different parser. The FastAPI “Request Files” page, “File Parameters with UploadFile” topic explains the multipart incoming-upload mechanism. By contrast, FastAPI “Stream JSON Lines” demonstrates an outgoing streaming response.

Recall before you move on

Why use maximum_record_bytes + 2 for the first read?

It allows a record exactly at the cap followed by CRLF to fit in the bounded read.

Why drain an oversized line through its newline?

The rest of that line belongs to the same record. Consuming it preserves the boundary before parsing the next record.

Why is a valid JSON array classified as not_object?

JSON syntax validity and the application's required record shape are separate checks.
