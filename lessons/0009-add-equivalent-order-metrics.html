Lesson 9 · Day 6 · Meaningful transformation

Enrich each clean order with item metrics

Compute the same two derived values with every selectable engine, prove semantic equivalence, and only then extend the DuckDB destination.

clean canonical NDJSON → selected adapter → enriched NDJSON → bounded DuckDB loader

1. Define the transformation

For every accepted order, add two top-level fields:

  • item_count: number of entries in order.items.
  • total_quantity: sum of every item's quantity.
{
  "record_number": 1,
  "order": {
    "items": [
      {"sku": "A", "quantity": 2},
      {"sku": "B", "quantity": 3}
    ]
  },
  "item_count": 2,
  "total_quantity": 5
}
These are derived facts, not new business rules. Every valid order remains present, its original cleaned fields remain unchanged, and source order is preserved.

2. Change the contract test first

Start with the deterministic two-record test in tests/test_processing_adapters.py. Change its expected output so both records contain the two derived fields. Keep the test parameterized over every selectable adapter.

Before editing production code, run only that test. The correct first result is a failure because the current adapters merely canonicalize and copy records.

.venv/bin/python -m pytest -q \
  tests/test_processing_adapters.py \
  -k order_records_and_fields_deterministically

3. Implement the Standard Python reference

After canonical validation, calculate:

items = order["items"]
item_count = len(items)
total_quantity = sum(item["quantity"] for item in items)

Write the enriched envelope one record at a time. Do not create a list of all orders. This implementation defines the correctness reference for the accelerated engines.

4. Express the same work lazily in Polars

Build both columns from the nested order.items list using Polars expressions, then select fields in the exact output order. Keep scan_ndjson() and sink_ndjson(engine="streaming"); do not call collect() merely to write the result.

Inspect the physical plan after adding the expressions. The desired shape remains a scan, streaming-compatible projection/expression work, and a sink. Measure memory instead of assuming it remains bounded.

5. Preserve the three-engine contract

The current project also exposes DuckDBAdapter as a selectable transformation engine. It must calculate the same fields in its SQL projection, or it must be removed deliberately from the selectable contract. It cannot silently produce a different schema.

6. Extend the DuckDB loader last

Only after adapter equivalence passes, add item_count and total_quantity columns to accepted_orders and include them in the parameterized insert. Keep the existing row/byte/item bounds, transaction, rollback, and idempotency behavior unchanged.

7. Required proof

  1. A two-item order produces item_count=2 and total_quantity=5.
  2. All selectable adapters produce byte-identical enriched NDJSON.
  3. Input order and nested item order remain unchanged.
  4. A later invalid record still removes partial adapter output.
  5. DuckDB stores the derived columns in the same batch transaction.
  6. Replay still inserts no duplicate rows.
  7. Benchmarks compare hashes, elapsed time, and peak RSS on equal work.
Polars may execute this expression faster, but the result is not assumed in advance. Correctness equivalence comes first; timing and memory measurement come afterward.
