Lesson 10 · CEO briefing · 2-hour preparation

Explain the project as an engineering decision story

Your goal is not to list files or FastAPI features. Your goal is to show that you understand the business problem, the failure modes of large imports, the chosen boundaries, the measured evidence, and the remaining production gap.

Open with this: “I built a FastAPI vendor-order import service that accepts large JSON or NDJSON files, keeps memory usage controlled by processing incrementally, produces auditable accepted and rejected records, supports interchangeable processing engines, and loads valid results into DuckDB in bounded, idempotent transactions.”

1. The problem we are solving

Vendors send order files that may be large, dirty, duplicated, malformed, or interrupted during upload. A simple endpoint using await file.read() and json.load() can make memory grow with the complete file, block useful work until parsing finishes, and provide poor recovery or audit information.

The design therefore optimizes for five properties:

  1. Bounded resource use: limit upload chunks, records, batches, nested items, database memory, and threads.
  2. Deterministic correctness: the same input and policy produce the same accepted, rejected, and processed output.
  3. Auditability: retain checksums, source record numbers, stable error codes, reconciled counts, and import states.
  4. Failure safety: temporary files, atomic replacement, database rollback, compensation, and replay checks prevent partial success from appearing complete.
  5. Replaceable performance: correctness is defined once; Python, Polars, or DuckDB can implement the clean transformation stage.

2. The end-to-end flow

HTTP multipart upload ↓ read fixed-size chunks; enforce total-byte limit; SHA-256 while copying staged file with generated name ↓ return 202 Accepted and queue background work import state: uploaded → queued → processing ↓ JSON array: incremental parse → clean → schema validate → business validate ↓ ↘ rejected.ndjson + stable reasons temporary SQLite spool → last-valid-wins duplicate decision ↓ accepted.ndjson (canonical contract) ↓ Python | Polars | DuckDB adapter → add item_count + total_quantity ↓ processed.ndjson ↓ row- and byte-bounded DuckDB transactions + idempotency ledger ↓ summary.json + completed / completed_with_errors / failed

What FastAPI owns

  • HTTP routes, multipart UploadFile, dependency injection, response models, generated OpenAPI documentation, middleware, exception translation, and background-task scheduling.
  • The upload route is async because it awaits incoming chunks. Blocking file writes are moved with asyncio.to_thread so they do not occupy the event-loop thread.
  • CPU-heavy parsing and database work execute after the 202 response. In this learning implementation that uses FastAPI BackgroundTasks; it is deliberately not claimed as a durable production queue.

What the domain/core layers own

  • Pydantic models define the HTTP and order contracts; the cleaning layer defines normalization policy; business validation defines supported currencies.
  • The parser, duplicate index, processing adapters, loader, and coordinator are plain Python components. This keeps business and data logic testable without starting an HTTP server.
  • Dependency injection supplies settings, services, the job repository, and writer lock. This makes dependencies explicit and replaceable in tests or a future deployment.

4. What has been completed so far

  1. API foundation: typed order contracts, nested validation, business validation, response filtering, consistent application errors, health endpoints, request IDs, and process-time headers.
  2. Architecture boundaries: routes, dependencies, services, configuration, exceptions, schemas, and core processing are separated and independently testable.
  3. Safe upload: multipart JSON/NDJSON, content-type checks, chunked reads, total-size enforcement, SHA-256, generated filenames, temporary-file cleanup, and atomic final rename.
  4. Large-file parsing: bounded NDJSON lines and incremental top-level JSON arrays, including malformed data and per-record size handling.
  5. Order pipeline: deterministic normalization, exact decimal policy, timezone normalization, nested validation, stable error mapping, import-wide duplicate policy, accepted/rejected artifacts, and reconciled summary.
  6. Engine abstraction: equivalent Standard Python, Polars, and DuckDB adapters derive item_count and total_quantity under a shared contract.
  7. Persistence and orchestration: bounded DuckDB transactions, idempotent batch replay, compensating cleanup, job-state endpoints, summaries, and bounded error retrieval.

Do not say “constant memory.” Say “bounded by configured chunks, record limits, batches, and engine behavior for the tested operations.” Libraries, buffers, the runtime, and more complex queries still consume memory.

6. The honest production-readiness answer

Say this directly: “The data-path design is production-oriented, but the orchestration is currently a single-process reference implementation.” Then name the boundaries:

  • Job state is in memory and disappears on restart.
  • FastAPI BackgroundTasks is not a durable queue and does not retry after process failure.
  • Uploads, artifacts, and the DuckDB database are on local storage.
  • The database-writer lock is process-local; multiple API workers do not share it.
  • The default API upload limit is 100 MiB; the 10-million-record fixture tested the parser path, not the default HTTP endpoint.
  • Current telemetry settings exist, but full production tracing/metrics/export and alerting are not yet integrated.

The production evolution is: durable object storage → durable job table plus outbox → message queue → leased worker with heartbeat/retries → manifest-based artifact publication → scalable serving database if concurrent writes are required.

8. Likely CEO questions and strong answers

“Why FastAPI?”

“It gives us typed request/response contracts through Pydantic, dependency injection, async request handling, OpenAPI documentation, and low ceremony around a modular Python data stack. FastAPI is the API boundary; efficient large-data handling comes from our streaming, batching, storage, and worker design—not from the framework name alone.”

“Can it handle a 2 GB or 10-million-row file?”

“The parser path has processed 10 million records at 18.51 MiB peak RSS on this development machine. That validates incremental parsing. The current HTTP endpoint intentionally defaults to a 100 MiB upload cap, so a 2 GB production claim requires setting an explicit capacity target and load-testing the full path: proxy, multipart handling, disk, parser, engine, database, concurrency, and recovery.”

“Why not just use Polars everywhere?”

“Raw-data recovery and business rejection need record-level control. We first create a canonical clean NDJSON boundary, then use Polars or DuckDB for transformations. In our 100k benchmark Polars was faster than Python but used about 3.1 times the peak RSS, so the engine remains configurable and Python is the conservative default.”

“Why SQLite and DuckDB together?”

“They solve different problems. Temporary SQLite is a disk-backed correctness structure for import-wide duplicate decisions and ordered spooling. DuckDB is the persistent analytical destination and batch-loading engine. The temporary SQLite file is deleted after outputs are published.”

“How do retries avoid duplicates?”

“Each batch has an import ID, batch number, checksum, and record count stored atomically with its rows. An identical replay is skipped; the same key with different content fails closed. A completed-import manifest also catches modified, truncated, or extended replays.”

“What happens when one record is bad?”

“A record-level validation failure is written to rejected.ndjson with a stable code and field location; valid records continue. The job ends completed_with_errors. A parser, engine, persistence, or publication failure is a job failure and triggers cleanup/rollback.”

“What would you build next?”

“First define the production SLO and largest supported file. Then replace process-local orchestration with durable object storage, job state, outbox/queue, and leased workers. Add end-to-end telemetry and representative concurrency/load tests before choosing the default accelerated engine.”
