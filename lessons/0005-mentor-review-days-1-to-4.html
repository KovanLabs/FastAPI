Lesson 0005 · Review preparation

Tell the story of Days 1–4

The project evolved from a typed FastAPI endpoint into a bounded large-file ingestion foundation. The important result is the set of engineering boundaries you can now defend.

Your 30-second opening

“I am building an order-import API in stages. By Day 4, I had implemented typed API contracts, separated HTTP and business concerns, persisted uploads safely in bounded chunks, and compared whole-document parsing with incremental parsing using measured memory results. The central lesson has been that validation, upload, parsing, and processing are different stages, and each needs its own contract and failure handling.”

The four-day progression

Day 1
Contracts

What I studied

FastAPI request locations, Pydantic models and nested types, response models, validation responses, status codes, and generated OpenAPI.

What I implemented

An order schema containing an ID, validated email, positive decimal amount, currency, datetime, status enum, and nested line items. I added order validation and CRUD-style routes, declared response models, and tested request bodies plus path, query, and header behavior.

What I learned

Schema validation answers “does this value have the declared shape and constraints?” Business validation answers questions such as “is this currency supported?” A response model is also an output boundary: it can prevent undeclared internal data from leaking.

Evidence: 20 focused tests passed.

Day 2
Boundaries

What I studied

Application assembly, routing, dependency injection, settings, service objects, stable exceptions, middleware, request correlation, lifespan, and event-loop blocking.

What I implemented

main.py assembles the application, middleware, lifespan, and global application-error handler. Routes live under app/api; an ordinary validation service lives under app/services; configuration and stable exceptions live under app/core. Dependencies construct the service at the FastAPI boundary.

What I learned

Dependency injection is valuable because business services remain ordinary Python and can be tested directly or replaced in route tests. I also measured that blocking work inside async def still blocks the event-loop thread: two blocking waits took about 0.305 seconds, while two awaited waits overlapped and took about 0.154 seconds.

Day 3
Uploads

What I studied

Multipart uploads, UploadFile, bounded reads, byte limits, streaming checksums, safe paths, temporary files, atomic publication, and cleanup after failures.

What I implemented

POST /imports accepts NDJSON or JSON, reads configured chunks, counts actual bytes, computes SHA-256 during the copy, stores under a generated identifier, and atomically replaces a temporary .part file only after success. Empty, oversized, interrupted, and failed writes remove partial files.

What I learned

Uploading and parsing are separate stages. Client filenames are metadata, not trusted paths. A size limit must be enforced while bytes arrive, not after loading the whole file. Temporary-write-then-rename prevents partially written files from looking complete.

Evidence: bounded reads stayed around 2 MiB of traced allocations for both 16 MiB and 64 MiB inputs; whole-file reads scaled to roughly 16 MiB and 64 MiB.

Day 4
Parsing

What I studied

NDJSON versus top-level JSON arrays, syntax parsing versus record processing, iterators, generators, recovery boundaries, per-record limits, incremental parsers, and peak RSS measurement.

What I implemented

The NDJSON parser reads a bounded line, rejects oversized records, drains the rest of an oversized line, enforces UTF-8, distinguishes blanks, invalid JSON, and non-object values, then continues at the next line. The JSON-array path reads fixed chunks and incrementally extracts array elements. Summary consumers keep counters and bounded error samples.

What I learned

NDJSON provides a natural recovery boundary at each line; a malformed top-level JSON array can invalidate the remaining document. More importantly, an incremental parser does not guarantee bounded memory—the caller must process and release each result. Calling list(iterator) destroys that benefit.

Evidence: for 100,000 records, json.load peaked at 162.37 MiB, streaming ijson.items at 18.29 MiB, and materialized ijson.items at 177.79 MiB. Ten million records were counted at 18.51 MiB peak RSS on this machine.

Architecture you should draw

HTTP multipart request → FastAPI route and media-type contract → bounded upload storage + checksum + atomic rename → format-specific parser (NDJSON or JSON array) → one record/outcome at a time → bounded summary counts and failure samples

Point out that Day 1 request validation and Day 4 import parsing are not the same thing. Imported records have not yet passed the planned Day 5 cleaner, Pydantic record schema, business rules, duplicate policy, or accepted/rejected writers.

Questions your mentor may ask

QuestionAnswer you should be able to give
Why not put every rule in the Pydantic model?Shape/type constraints and business policy change for different reasons. The service owns supported-currency policy and stays independently testable.
Why use asyncio.to_thread?File writes and synchronous parsing are blocking work. Moving them off the event-loop thread keeps unrelated async requests responsive; it does not make the operation inherently faster.
Why generate the stored filename?A client filename is untrusted input and may contain unsafe or colliding paths. The server owns storage identity and preserves only the approved suffix.
Why hash while copying?The bytes are already passing through the loop, so the checksum can be computed without another whole-file read or keeping the file in memory.
Why can NDJSON recover after bad JSON?Each physical line is an independent record boundary. After rejecting one line, parsing can resume at the next line.
Why is a JSON array harder?Element boundaries depend on document syntax, nesting, strings, and escapes. Broken structural syntax may make the remainder untrustworthy.
Does “streaming” guarantee low memory?No. The parser may yield lazily, but a consumer that builds a list retains every object. Bounded behavior is an end-to-end property.
Why cap failure samples but count every failure?Operators need exact totals, but retaining every error makes memory grow with bad input. Bounded samples preserve diagnostic value without unbounded storage.
What is deliberately unfinished?Field cleaning policy, per-record Pydantic and business validation, import-scope duplicates, accepted/rejected NDJSON outputs, and final count reconciliation belong to Day 5.

Your closing

“The main change in my thinking is that bounded ingestion is an end-to-end design property. Uploading in chunks is not enough; parsing, consumers, summaries, and later duplicate tracking must also avoid retaining input-sized state. I now try to state each boundary and prove it with focused tests or measurements.”
