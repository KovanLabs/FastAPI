FastAPI Days 1 to 5

A technical and theoretical explanation of the Vendor Order Import API: what every layer does, why the functions exist, how a request or file moves through the system, and which parts are active, standalone, legacy, or still awaiting orchestration.

The whole project in one picture

HTTP request → FastAPI route and declared HTTP contract → Pydantic request schema or UploadFile → dependency-built service / bounded upload storage → format parser → deterministic cleaner → Pydantic record validation → business validation → import-wide duplicate decision in SQLite → accepted.ndjson + rejected.ndjson + reconciled summary

Days 1–5 do not build this entire arrow as one HTTP operation. Days 1–4 build and expose the API, upload, and parser boundaries. Day 5 builds the canonical processing engine as a standalone file pipeline called by scripts/process_orders.py. Connecting that engine to an import job is later orchestration work.

Day 1 — FastAPI and HTTP contracts

Theory

An API contract states the method, path, input location, input schema, success status, response schema, and failure behavior. FastAPI reads a route function signature to decide whether data comes from the path, query string, dependency graph, request body, or uploaded form data.

Pydantic provides structural validation: types, required fields, length/range constraints, nested objects, enums, email syntax, decimal conversion, and datetime parsing. A business rule is different. “Currency is a three-character string” is schema validation; “only INR, USD, and EUR are supported” is business policy.

A response model is not documentation only. FastAPI serializes and filters the returned object through it, so undeclared internal fields do not become public accidentally.

Schemas

app/schemas/orders.py declares the vocabulary of an order.

  • OrderStatus is a string enum. Only pending, completed, and cancelled are accepted.
  • Sku is an Annotated string with whitespace stripping and length constraints.
  • OrderItem requires a SKU and an integer quantity from 1 through 10,000.
  • OrderCreate is the canonical incoming order shape: ID, validated email, positive Decimal, three-character currency, datetime, status, and at least one nested item.
  • ShippingAddress and CheckoutOrderRequest demonstrate nested request models.
  • OrderResponse inherits every OrderCreate field and adds accepted=True.

Day 2 — Application structure, dependencies, and execution

Architecture

The folders separate reasons to change:

  • app/main.py assembles the application and cross-cutting behavior.
  • app/api/ owns HTTP routes and FastAPI dependency wiring.
  • app/schemas/ owns public data shapes.
  • app/services/ owns framework-independent business operations.
  • app/core/ owns configuration, errors, files, parsing, cleaning, and processing infrastructure.

This structure matters because HTTP, configuration, policy, and file processing have different tests and change at different rates.

Exceptions

ApplicationError stores a stable error_code, HTTP status_code, human message, and structured details. Subclasses specialize the public meaning: upload too large (413), empty upload (400), storage failure (503), unsupported media type (415), unsupported currency (422), duplicate order (409), missing order/import (404), and unavailable storage (503). Central handling prevents every route from rebuilding error JSON.

Day 3 — Receiving large uploads safely

Theory

UploadFile represents one multipart file field. It is not parsed JSON. The upload stage must verify media type, enforce the real byte limit while reading, avoid trusting a client filename, clean up partial data, and return a stable source identity.

Bounded reading means each call asks for at most a configured chunk. It does not mean total memory is automatically bounded everywhere; later stages must also avoid retaining the entire dataset.

Writing to a temporary file and replacing the final path only after success gives a publication boundary: readers never mistake a partially written file for a completed upload. os.replace() is atomic for one destination on the same filesystem.

Functions
Function / typeWhat it does and why
ImportResultAn immutable dataclass returning import ID, SHA-256 checksum, safe stored filename, and byte count.
AsyncReadableA protocol requiring only async read(size). This keeps store_upload() decoupled from FastAPI's concrete UploadFile and makes fakes easy in tests.
store_upload(source, settings, suffix)Generates a UUID identity and server-owned path; opens a unique .part file; repeatedly reads configured chunks; rejects a chunk that would exceed the total limit; writes through asyncio.to_thread(); updates SHA-256 in the same pass; rejects empty input; atomically replaces the final path; removes the temporary file for size, empty, I/O, cancellation, or other failure; returns metadata only after success.
import_orders(settings, file)Normalizes the MIME type, maps supported types to approved suffixes, stores the bytes, and returns HTTP 202 with state queued. It intentionally does not parse or process the file.

Why hash during the copy? The bytes already pass through the loop, so one pass supplies integrity/source identity without rereading or retaining the file.

Evidence: 12 upload tests passed. In the recorded experiment, whole reads scaled from roughly 16 to 64 MiB, while 1 MiB chunked reads stayed near 2 MiB of traced Python allocations.

Day 4 — Incremental JSON parsing

Theory

NDJSON contains one complete JSON value per physical line. A bad line can be rejected and parsing can resume at the next line. A JSON array is one document; element boundaries depend on commas, nesting, string literals, and escapes. Broken structural syntax can invalidate the remainder.

An iterator or generator is lazy: it can produce one result before all results exist. But streaming is an end-to-end property. list(iterator) retains every yielded object and eliminates the main memory advantage.

A parser checks bytes, UTF-8, and JSON syntax. It does not automatically enforce the order schema or business rules.

Experiments

make_order() creates one deterministic generated record with controlled anomalies. write_orders() streams a valid top-level array to disk instead of building it in memory. The script main() parses CLI arguments and writes the fixture.

custom_records() yields through the custom array parser; ijson_records() yields through ijson.items(); consume() either counts lazily or deliberately materializes with list(); the comparison main() measures elapsed time and process peak RSS.

For 100,000 records: json.load() peaked at 162.37 MiB, lazy custom parsing at 18.28 MiB, lazy ijson at 18.29 MiB, and materialized incremental iterators around 175–178 MiB. Ten million ijson records were counted at 18.51 MiB peak RSS on the recorded machine. These are machine-specific measurements; the general result is the retention behavior.

stream_items() in app/day-04_sample.py demonstrates an outgoing async iterable response. It does not parse an uploaded file. Direction and format must not be confused.

Day 5 — Cleaning, validation, duplicates, and rejection handling

Theory

Day 5 separates four questions:

  1. Cleaning: which approved source representations become one canonical representation?
  2. Schema validation: does the cleaned value satisfy OrderCreate?
  3. Business validation: is the otherwise valid order allowed by current policy?
  4. Import decision: which valid duplicate wins, and what output receives every source record?

A deterministic cleaner gives the same result for the same input. An idempotent cleaner satisfies clean(clean(x)) == clean(x) for accepted values. Stable machine codes are project-owned; human messages may change without breaking clients. Nested locations such as ("items", 0, "sku") preserve exactly where a problem occurred.

Duplicate policy

The policy is last valid record wins within one import. Invalid records never update the winners table, so a later invalid duplicate cannot displace an earlier valid order. A later valid duplicate replaces the winner row; during pass two, every earlier valid occurrence is rejected.

Why SQLite instead of a Python set? The measured peak for 100,000 generated IDs was about 114 bytes per ID, projecting roughly 1.14 GB of traced Python heap for 10 million IDs, before other pipeline memory. SQLite moves import-wide state to a bounded disk-backed working store.

A source record traced end to end

{
  "order_id": " ord-1001 ",
  "customer_email": "USER@EXAMPLE.COM ",
  "amount": "12.345",
  "currency": " inr ",
  "ordered_at": "2026-10-07T10:30:00+00:00",
  "status": "PENDING",
  "items": [{"sku": " sku-1 ", "quantity": 2}]
}
  1. The JSON-array parser yields a Python dictionary without loading the full array.
  2. The cleaner produces ORD-1001, lowercase email, Decimal("12.35"), INR, an Asia/Kolkata-aware datetime, pending, and trimmed SKU.
  3. TypeAdapter(OrderCreate) confirms the canonical schema and nested constraints.
  4. Business validation confirms that INR is configured as supported.
  5. SQLite records this valid record and makes its canonical ID the current winner.
  6. After all records are seen, pass two writes it to accepted output only if no later valid record with the same canonical ID exists.

Core theoretical lessons

  1. Validation is layered. JSON syntax, Pydantic schema, business policy, and duplicate policy answer different questions.
  2. Bounded memory is end to end. Chunked upload or lazy parsing alone is insufficient if a later consumer builds a full list or set.
  3. Recovery needs a trustworthy boundary. NDJSON has a physical line boundary; a malformed array may not.
  4. Stable contracts belong to the application. Public error codes and canonical output must not depend directly on changeable library wording.
  5. Correctness precedes acceleration. Day 5 freezes a standard-Python golden result before alternative engines are compared.
  6. Durability has levels. Temporary write plus replace protects one file; rollback improves a two-file normal-failure case; neither creates a database-grade distributed transaction.
  7. Measurements need scope. tracemalloc measures traced Python allocations; RSS includes more process memory. Results from one machine are evidence, not universal guarantees.
