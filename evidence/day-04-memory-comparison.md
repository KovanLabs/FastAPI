# Day 4 JSON-array memory comparison

## Fixture and method

The focused comparison used `/tmp/orders_100k.json`, generated by
`scripts/generate_orders_json.py`. It contains 100,000 order objects and is
22,158,173 bytes. Each strategy ran in a fresh Python process so its reported
peak resident set size (RSS) was independent of the other strategies.

Run a strategy with:

```bash
.venv/bin/python -m scripts.compare_json_memory /tmp/orders_100k.json \
  --strategy custom
```

Add `--materialize` to deliberately convert an incremental iterator to a list.

## Results on this development machine

| Strategy | Materialized? | Records | Seconds | Peak RSS (MiB) |
|---|---:|---:|---:|---:|
| `json.load` | inherently yes | 100,000 | 0.509 | 162.37 |
| custom incremental parser | no | 100,000 | 9.568 | 18.28 |
| custom incremental parser | yes | 100,000 | 9.525 | 175.21 |
| `ijson.items` | no | 100,000 | 0.434 | 18.29 |
| `ijson.items` | yes | 100,000 | 0.943 | 177.79 |

These measurements are evidence from one machine, not universal performance
guarantees. The stable conclusion is behavioral: `json.load()` constructs the
whole top-level array, and `list(iterator)` deliberately retains every yielded
object. Incremental iteration keeps only the current object and parser buffers
when the caller processes each object and releases it.

The complete `data/samples/orders_10m.json` fixture was also counted with
`ijson.items` without list conversion: 10,000,000 records, 44.734 seconds, and
18.51 MiB peak RSS on this machine.

## Design comparison

- The custom parser makes the application's raw byte limit explicit and reports
  `RecordTooLargeError`. Its Python byte-by-byte scanner is comparatively slow.
- `ijson.items(source, "item")` is mature, faster here, validates the entire JSON
  stream, and provides sync and async interfaces. Its high-level `items` API does
  not directly enforce this project's raw-byte size limit per array element.
- `json.load(source)` is simplest when the whole document comfortably fits in
  memory. It is unsuitable for the 2.2 GB fixture under ordinary API memory
  budgets because it builds the entire array before returning.
- Converting either incremental iterator with `list(...)` removes the primary
  memory advantage. Future Polars cleaning should therefore receive bounded
  batches rather than one list containing every order.
