The app/ folder, line by line

Every non-blank source line is represented below. Lines belonging to one multi-line Python statement are grouped, because they perform one operation. Blank lines have no runtime effect; they visually separate imports, classes, and functions according to normal Python style.

The shortest mental model: main.py assembles the app; api/ exposes HTTP; schemas/ defines data contracts; services/ holds business rules; and core/ supplies configuration, errors, storage, uploads, and parsing.

Important findings

First, see the whole request flow

Client → ASGI server → RequestContextMiddleware → FastAPI router → dependency resolution → Pydantic input validation → route function → service/core code → response_model serialization → middleware headers → Client Raised ApplicationError → global exception handler → stable JSON error response

That flow explains the folder boundaries. HTTP-specific decisions stay in api/; reusable validation stays in services/; data shapes stay in schemas/; infrastructure stays in core/; assembly stays in main.py.

Important findings the line-by-line view reveals

  1. The active import endpoint stores but does not parse. It returns state="queued", but there is no queue or worker connected yet.
  2. The parser contract and its test disagree. The implementation raises on malformed NDJSON; the test expects an outcome object and continued processing.
  3. The incremental JSON-array parser has correctness risks. Opening-depth accounting, rescanning preserved bytes, end-of-input validation, comma validation, and early size enforcement need tests/fixes before use.
  4. Creation and validation are inconsistent. POST /orders/validate checks supported currency, while POST /orders does not.
  5. Several pieces are planned but unused. environment, telemetry settings, progress interval, ImportNotFoundError, and ensure_storage_directories do not affect current requests.
