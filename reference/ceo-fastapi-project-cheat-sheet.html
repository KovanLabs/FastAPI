Vendor Order Import API

A bounded, auditable, engine-neutral pipeline for large vendor order files.

One sentence: The service streams and stages uploads, incrementally cleans and validates orders, separates accepted and rejected records, enriches valid data through a selectable engine, and loads it into DuckDB in bounded idempotent transactions.

Architecture in one view

upload → stage + SHA-256 → 202 + state machine → incremental parse → clean → Pydantic schema → business rules → SQLite duplicate spool → accepted/rejected NDJSON → Python|Polars|DuckDB enrichment → bounded DuckDB batches → summary/status/errors

Five design principles

  1. Bound resources at every boundary, not only at upload.
  2. Separate raw-data recovery from accelerated clean-data transforms.
  3. Make correctness deterministic and observable before optimizing speed.
  4. Publish safely with temporary files, replacement, transactions, and compensation.
  5. Keep infrastructure replaceable behind repository, adapter, and loader interfaces.

Proof points

100k enginesPython 10.6 s / 77.7 MiB; Polars 6.1 s / 238.6 MiB; DuckDB 6.0 s / 171.5 MiB.
EquivalenceAll three processed outputs had identical size and SHA-256 for the benchmark fixture.
VerificationRecorded external run: 236 tests passed in 16.29 s.

Why FastAPI

Typed Pydantic contracts, dependency injection, async upload handling, OpenAPI documentation, middleware, and clear error/response models. FastAPI is the HTTP layer; scalability comes from the pipeline architecture.

Current status

Implemented: API contracts, upload safety, JSON/NDJSON streaming, deterministic cleaning/validation, duplicate policy, three equivalent transformation engines, transactional/idempotent loading, state/status/summary/error APIs, tests and benchmarks.

Not yet production durable: in-memory job state, in-process background tasks, local files, process-local writer lock, incomplete production telemetry.

Next: define SLO/capacity → object storage → durable job/outbox → queue + leased workers → production database choice → observability and end-to-end load/recovery tests.
